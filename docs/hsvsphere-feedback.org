* Reading guide

The first part records the desired product behavior. It intentionally describes
what Autolith should become without prescribing a detailed implementation. The
original discussion and Lukáš's later clarifications are preserved verbatim at
the end.

* Direction

Autolith should feel like one live Common Lisp system with an LLM attached, not
like separate chat, slash-command, Lisp, and tool interfaces which happen to
share a terminal.

This does not mean removing useful boundaries such as named isolated Lisp
workers, recovery, authorization, or durable mutation. It means giving the user
and the agent one coherent Lisp-shaped interaction model across those
boundaries.

* Product principles

- Lisp is the canonical interaction language.
- Ordinary prose remains convenient and does not require ceremony.
- The same named operation has the same meaning regardless of whether the user
  or the agent invokes it.
- The interface remains honest about what the provider actually sent.
- Autolith keeps normal terminal scrollback rather than becoming a fullscreen
  application.

* Ordered scope

** 1. Lisp-first input

- Input beginning with =(= is arbitrary Lisp evaluated in the live Autolith
  context.
- Parenthesized input is explicit user intent. It executes directly and does not
  require the LLM to acknowledge or reinterpret it first.
- While Lisp input is being composed, the normal =>= prompt marker changes to a
  red =*=. It changes back if the input no longer begins with =(=.
- Parenthesized input is syntax-highlighted with the project's ColorLisp library
  while it is being edited, not only after submission.
- Lisp input supports normal multiline forms and presents values, multiple
  values, conditions, and restarts like a real REPL.
- Ordinary prose remains convenient. Conceptually, prose is sugar for a
  =prompt= operation, with image attachments and other input data preserved.

** 2. One callable operation surface

- Interactive commands, model tools, and user-callable operations are one
  user-visible concept.
- Canonical calls are Lisp forms such as =(help)= and
  =(fs.list :path ".")=.
- User-entered and agent-requested calls reach the same named operation and
  produce the same kind of result.
- Authority still follows the caller. A form typed by the user is an explicit
  user request; an agent-generated call still obeys its approval and permission
  policy.
- Named isolated Lisp workers remain useful because they target separate heaps,
  but they are invoked through the same Lisp-shaped surface.
- Arbitrary Lisp remains legal when typed explicitly even when it is not a
  registered operation.

** 3. Completion and slash compatibility

- Existing =/command= input remains accepted as compatibility sugar for the
  corresponding Lisp call.
- After executing a slash spelling, Autolith shows the preferred parenthesized
  spelling as a short hint.
- =(help)= is canonical. =/help= remains a compatibility spelling rather than a
  separate facility.
- Typing either =/= or =(= offers registered user-facing operations.
- Completion does not dump every symbol from the image. This restriction affects
  suggestions only; it does not restrict arbitrary Lisp entered manually.
- Tool operations such as =fs.list= are easy to discover and call from the same
  completion system as commands such as =help=.

** 4. Lisp-shaped transcripts

- A user-entered Lisp call is displayed exactly as submitted.
- A model tool call keeps its canonical tool name and displays a deterministic,
  syntax-highlighted Lisp form because the provider call has no original spelling.
- Autolith must not claim that a provider-originated tool call was literally sent
  as Lisp.
- Normal operation display should not expose recipient blocks or raw JSON
  arguments when a readable Lisp form exists.
- Results and failures are presented as the result of the visible operation,
  rather than as output from a separate hidden command language.

** 5. Active-turn behavior and status

- Only work that genuinely requires the agent to be idle is scheduled.
- Operations may run immediately when they do not conflict with the active turn.
  Work which needs an agent boundary or turn completion waits for that boundary.
- There is an explicit way for the local user to force immediate evaluation. Its
  name remains undecided.
- The =READ / EVAL / PRINT / LOOP= status row remains an animation. It is not a
  literal indication of the current execution phase.
- Current tool use, active message or streaming activity, local evaluation, and
  sub-agent activity are displayed below the status row, never above it.
- Scheduled and queued work is also displayed below the status row, but only work
  which actually must wait is described as scheduled.
- When scheduled work runs, its result is visible to the user and, when relevant,
  to the agent.

** 6. Terminal prompt markers

- Autolith emits terminal shell-integration markers for prompt start, input
  start, execution start, and completion status.
- These markers make prompt-block navigation, selection, and status recognition
  work in ordinary terminal scrollback.
- Prompt markers describe user interaction blocks. They are not emitted for
  every internal repaint or every model tool call.
- This feature must preserve Autolith's non-fullscreen terminal design.

* Component ownership

- Autolith owns input meaning, operation policy, live-region ordering, status-row
  presentation, transcript representation, and the points where prompt markers
  are emitted.
- Clinedi owns generic editing, completion, and rendering mechanics. It should
  not decide what an Autolith prompt or operation means, or what activity belongs
  above or below the status row.
- cl-colorist remains a styling and ANSI-aware text library. Prompt-marker
  semantics do not belong there.
- ColorLisp supplies the Lisp syntax highlighting used for parenthesized prompt
  input.
- CCLSH should emit the same class of prompt markers from its own shell loop.
  Application semantics remain in each application even if a small low-level
  facility is shared later.

* Existing behavior to retain or correct

- Follow-up and scheduled previews already appear below the status row. Preserve
  that ordering.
- Other current activity, including sub-agents, can appear above the status row.
  The desired order places the animated status row first and all current activity
  beneath it.
- The =READ / EVAL / PRINT / LOOP= animation should remain an animation, not
  become a semantic phase display.
- Autolith currently has distinct interactive-command and model-tool surfaces.
  The desired product direction is one user-visible operation model.

* Non-goals

- Do not turn Autolith into a fullscreen TUI.
- Do not advertise every internal function through completion.
- Do not erase the distinction between the active image and isolated worker
  heaps.
- Do not weaken agent-call approval merely to make the syntax look unified.
- Do not pretend that out-of-band provider messages were originally Lisp text.

* Open product decisions

- Whether prose input stays visually as prose or is shown expanded as a
  =prompt= form.
- Whether results from arbitrary local Lisp automatically enter later model
  context.
- The name and exact scope of the immediate-evaluation override.
- Whether the preferred-form hint appears every time, once per command, or once
  per session.

A prompt marker is an invisible terminal escape sequence emitted by a shell to indicate semantic boundaries such as:

prompt begins
prompt ends and user input begins
command execution begins
command output ends

Terminal emulators use these markers for shell integration features like command-block navigation, output selection, prompt detection, and exit-status display.

A common protocol uses OSC 133 sequences:

ESC ] 133 ; A ST    prompt begins
ESC ] 133 ; B ST    prompt ends and user input begins
ESC ] 133 ; C ST    command execution begins
ESC ] 133 ; D ; 0 ST command finishes with status 0

They occupy no screen cells and are not visible text. Without markers, a terminal can only heuristically guess where prompts and commands are. These are distinct from shell/readline delimiters such as \[ and \], which merely tell the shell that enclosed prompt characters have zero display width.
